# Deployment

Release with the `Tinfoil Release` workflow, which writes the measured image digest into `tinfoil-config.yml`. Provision `USAGE_REPORTER_SECRET` before deploying; startup fails without it.

## Long inputs and the forward queue

A `/redact` request is proxied to one worker process, which tokenizes the text and cuts it into windows of `OPF_WINDOW_TOKENS` tokens (default 6144) that overlap by `2 × OPF_WINDOW_OVERLAP` (default 1024 each side), so the effective stride is `OPF_WINDOW_TOKENS − 2 × OPF_WINDOW_OVERLAP` (4096); an input that fits in one window is not cut at all. Only the tokens with `OPF_WINDOW_OVERLAP` tokens of context on both sides are kept from each window, except at the sequence ends. The model is banded attention with `bidirectional_{left,right}_context` = 128 over `num_hidden_layers` = 8, so a token's scores depend on at most ±1024 neighbours; with the overlap at or above that receptive field every token is scored exactly as in one long forward pass, and the stitched scores then go through upstream `opf`'s unchanged global Viterbi decode. The worker reads those fields from the checkpoint `config.json` at startup and **refuses to start** if `OPF_WINDOW_OVERLAP` is below `layers × context`; the env may raise the overlap, never lower it below exact.

Each window also runs at its **absolute token position** (the coordinator sends the window's offset on `X-Tinfoil-Position-Offset`; the worker points the model's rotary cos/sin caches at that offset for the forward). Without this every window would restart at position 0 and its scores would differ from a single pass by float32 angle rounding — measured at ~1e-2 in log-probability, the same size as prepending one token to the document, flipping ~0.03% of borderline spans. With it the stitched scores match a single pass to GEMM rounding.

The windows are posted concurrently to the gateway's internal `POST /forward` (raw little-endian int32 token ids in, row-major float32 log-probabilities out with the `rows,classes` shape in `X-Tinfoil-Shape`; binary because a window's scores are thousands × classes floats). The gateway schedules windows onto lanes (`OPF_WORKERS × OPF_MAX_CONCURRENCY` of them, spread over the workers):

- Windows of **short requests** (total tokens ≤ `OPF_SHORT_REQUEST_TOKENS`, default one window; the coordinator sends the request total on `X-Tinfoil-Request-Tokens`) go to the front of the queue, FIFO.
- Long requests have one FIFO queue per caller (keyed by a hash of the credential the `/redact` proxy stamps on `X-Tinfoil-Key-Hash`), served round-robin, each window to the worker with the fewest forwards in flight.
- **Predicted-short-lane rule**: the gateway predicts when each busy lane frees from its window's token count × an EWMA of ms/token (seeded by `OPF_MS_PER_TOKEN`, default 0.5, the TDX-measured rate at 4 workers × 8 threads; exported as `pii_forward_ms_per_token`). A long window may take a free lane only if, among the _other_ lanes, the k-th soonest-freeing one is predicted free within the k-th entry of `OPF_SHORT_LANE_HORIZONS` (default `0.5,1.5` seconds); otherwise it is held until a lane frees or the prediction comes within range. Short windows ignore the rule. `""`/`0` disables it; `OPF_SHORT_LANE_ARMED_SECONDS` (default 30) applies it only while a short request has been seen within that many seconds, so an idle night runs flat out; `0` applies it always. The rule's cost — lane-seconds left idle while a long window waited — is exported as `pii_forward_hold_seconds_total`.

`/forward` is internal: the gateway only accepts it from loopback and the shim does not expose it. The Python worker's `/forward` listens on loopback only. The gateway hands each worker it spawns `OPF_FORWARD_URL` (its own `/forward` unless the deployment overrides it); a worker started by hand without it runs windows in-process (single-worker development).

## Limits

Requests are capped at 4 MiB (≈250 windows at the default geometry), and that is a normal request, not an overload. There is no token limit; load is bounded in windows and time:

- A `/redact` request may run for 30 s plus `OPF_WINDOW_TIMEOUT_SECONDS` (default 5, generous against the ~3 s measured per 6144-token window under TDX) per window, estimated by the gateway from the body size (one token per four bytes), capped at `OPF_MAX_REQUEST_SECONDS` (default 900). The ceiling also bounds how long a window may wait in the forward queue and the server's read and idle timeouts.
- The timeouts above are size allowances, not wedge detectors. The wedge detector is per dispatch: each gateway→worker forward must finish within `OPF_FORWARD_TIMEOUT_SECONDS` (default 30, ~40× a window). A forward that does not returns 504 to the coordinator, which fails the whole `/redact` (no partial result, no billing event), increments `pii_forward_timeouts_total` on the gateway and `pii_filter_forward_failures_total{status="504"}` on the coordinator, and marks that worker unhealthy: `/health` then fails until the container is replaced.
- When more than `OPF_MAX_QUEUED_WINDOWS` windows (default 4096) are waiting for a forward lane, new windows get 503 and the request that owns them fails with 503, cancelling its remaining windows. A window that cannot start within the ceiling is also refused with 503.
- The coordinating worker keeps at most `OPF_FORWARD_FANOUT` windows (default 2 × `OPF_WORKERS` × `OPF_MAX_CONCURRENCY`) in flight to the gateway per request, enough to keep every lane busy while the gateway queue does the scheduling.

On shutdown the front end drains for up to 30 seconds, then flushes queued usage events.

## Usage reporting

Each HTTP 200 from `/redact` queues one usage event for the authenticated caller in the router's `model_request` shape (`model: pii-filter`, `route: /redact`) with an `input_tokens` meter carrying the request's tokenized length, and returns `X-Tinfoil-Billable-Requests: 1`, which websearch and the router use as the billing receipt. The control plane prices the event from the model catalog: input tokens at the per-token rate plus the per-request price, which acts as the floor for short calls. The coordinating worker returns the token count on an internal `X-Tinfoil-Input-Tokens` response header; the gateway strips it before the response reaches the client and refuses (502) a 200 that lacks it rather than return an unmetered result. The header acknowledges a queued event, not settlement: failed deliveries are dropped, so monitor `pii_usage_failed_total` and `pii_usage_dropped_total`. Delivery needs egress to `api.tinfoil.sh`. The gateway's `/metrics` also reports `pii_forward_queued`, `pii_forward_inflight`, `pii_forward_timeouts_total`, `pii_forward_hold_seconds_total` and `pii_forward_ms_per_token` alongside worker 0's model metrics (`pii_filter_input_tokens` histogram with buckets 128…64k — `_sum` is the token total, `pii_filter_windows_total`, `pii_filter_window_roundtrip_seconds`, `pii_filter_forward_duration_seconds`).
