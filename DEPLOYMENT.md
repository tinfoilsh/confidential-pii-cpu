# Deployment

Release with the `Tinfoil Release` workflow, which writes the measured image digest into `tinfoil-config.yml`. Provision `USAGE_REPORTER_SECRET` before deploying; startup fails without it. `USAGE_CONTEXT_SECRET` (the platform's usage-context signing key, shared with websearch and the router) lets the gateway verify the context a parent service sends with a nested call; without it contexts are ignored and every call is treated as direct.

## Long inputs and the forward queue

A `/redact` request is proxied to one worker process's `/chunk`, which tokenizes the text and cuts it into windows of `OPF_WINDOW_TOKENS` tokens (default 6144) that overlap by `2 × OPF_WINDOW_OVERLAP` (default 1024 each side), so the effective stride is `OPF_WINDOW_TOKENS − 2 × OPF_WINDOW_OVERLAP` (4096); an input that fits in one window is not cut at all. Only the tokens with `OPF_WINDOW_OVERLAP` tokens of context on both sides are kept from each window, except at the sequence ends. The model is banded attention with `bidirectional_{left,right}_context` = 128 over `num_hidden_layers` = 8, so a token's scores depend on at most ±1024 neighbours; with the overlap at or above that receptive field every token is scored exactly as in one long forward pass, and the stitched scores then go through upstream `opf`'s unchanged global Viterbi decode. The worker reads those fields from the checkpoint `config.json` at startup and **refuses to start** if `OPF_WINDOW_OVERLAP` is below `layers × context`; the env may raise the overlap, never lower it below exact.

Each window also runs at its **absolute token position** (the coordinator sends the window's offset on `X-Tinfoil-Position-Offset`; the worker points the model's rotary cos/sin caches at that offset for the forward). Without this every window would restart at position 0 and its scores would differ from a single pass by float32 angle rounding — measured at ~1e-2 in log-probability, the same size as prepending one token to the document, flipping ~0.03% of borderline spans. With it the stitched scores match a single pass to GEMM rounding.

Every window of the request is posted at once to the gateway's internal `POST /queue` (raw little-endian int32 token ids in, row-major float32 log-probabilities out with the `rows,classes` shape in `X-Tinfoil-Shape`; binary because a window's scores are thousands × classes floats). The gateway owns the queue and schedules windows onto lanes, one per worker (a worker process runs one forward at a time: one interpreter, one torch pool, one rotary offset):

- Windows of **short requests** (total tokens ≤ `OPF_SHORT_REQUEST_TOKENS`, default one window; the coordinator sends the request total on `X-Tinfoil-Request-Tokens`) are served before long ones.
- Within each class callers (keyed by a hash of the credential the `/redact` proxy stamps on `X-Tinfoil-Key-Hash`) are served round-robin, FIFO per caller, so a caller's windows only ever wait behind its own; each window goes to the worker with the fewest forwards in flight.
- Each `/redact` gets an id (`X-Tinfoil-Request-ID`, handed to the coordinator and echoed on each window it queues). When the `/redact` ends for any reason — answered, past its deadline, or the client gone — the gateway drops that request's queued windows and refuses their pending `/queue` posts (409), which fails the coordinator's task group and stops it. Windows already on a lane finish.
- **Predicted-short-lane rule**: the gateway predicts when each busy lane frees from its window's token count × an EWMA of ms/token (seeded by `OPF_MS_PER_TOKEN`, default 0.5, the TDX-measured rate at 4 workers × 8 threads; exported as `pii_forward_ms_per_token`). A long window may take a free lane only if, among the _other_ lanes, the k-th soonest-freeing one is predicted free within the k-th entry of `OPF_SHORT_LANE_HORIZONS` (default `0.5,1.5` seconds); otherwise it is held until a lane frees or the prediction comes within range. Short windows ignore the rule. `""`/`0` disables it; `OPF_SHORT_LANE_ARMED_SECONDS` (default 30) applies it only while a short request has been seen within that many seconds, so an idle night runs flat out; `0` applies it always. The rule's cost — lane-seconds left idle while a long window waited — is exported as `pii_forward_hold_seconds_total`.

`/queue` is internal: the gateway only accepts it from loopback and the shim does not expose it; it relays each window to a worker's `/forward` (one model pass over one window), which listens on loopback only. The gateway hands each worker it spawns `OPF_QUEUE_URL` (its own `/queue` unless the deployment overrides it); a worker started by hand without it runs windows in-process (single-worker development).

## Limits

Inputs are capped at `OPF_MAX_INPUT_TOKENS` (default 80,000; longer inputs get 413 with the limit in the message — chunking is exact at any length, the cap keeps absolute positions inside the range validated in the lab) and bodies at 4 MiB. An 80k-token request is ~20 windows and a normal request, not an overload. There is no token limit; load is bounded in windows and time:

- A `/redact` request may run for 30 s plus `OPF_WINDOW_TIMEOUT_SECONDS` (default 5, generous against the ~3 s measured per 6144-token window under TDX) per window, estimated by the gateway from the body size (one token per four bytes), capped at `OPF_MAX_REQUEST_SECONDS` (default 900). The ceiling also bounds how long a window may wait in the forward queue and the server's read and idle timeouts.
- The timeouts above are size allowances, not wedge detectors. The wedge detector is per dispatch: each gateway→worker forward must finish within `OPF_FORWARD_TIMEOUT_SECONDS` (default 30, ~40× a window). A forward that does not returns 504 to the coordinator, which fails the whole `/redact` (no partial result, no billing event), increments `pii_forward_timeouts_total` on the gateway and `pii_filter_forward_failures_total{status="504"}` on the coordinator, and marks that worker unhealthy: `/health` then fails until the container is replaced.
- When more than `OPF_MAX_QUEUED_WINDOWS` windows (default 4096) are waiting for a forward lane, new windows get 503 and the request that owns them fails with 503, cancelling its remaining windows. A window that cannot start within the ceiling is also refused with 503.

On shutdown the front end drains for up to 30 seconds, then flushes queued usage events.

## Usage reporting

Each HTTP 200 from `/redact` queues one usage event for the authenticated caller in the router's `model_request` shape (`model: pii-filter`, `route: /redact`) with an `input_tokens` meter carrying the request's tokenized length, and returns the billing receipt `X-Tinfoil-Billable-Requests: 1` with `X-Tinfoil-Billable-Input-Tokens: <n>`, which websearch sums and the router prices for its cost trailer. The control plane prices the event from the model catalog: input tokens at the per-token rate plus the per-request price, which acts as the floor for short calls. A nested call whose parent context says the customer request is already counted (`bill_customer_request: false`) reports zero customer requests and only its tokens, as websearch does. The coordinating worker returns the token count on an internal `X-Tinfoil-Input-Tokens` response header; the gateway strips it before the response reaches the client and refuses (502) a 200 that lacks it rather than return an unmetered result. The header acknowledges a queued event, not settlement: failed deliveries are dropped, so monitor `pii_usage_failed_total` and `pii_usage_dropped_total`. Delivery needs egress to `api.tinfoil.sh`. The gateway's `/metrics` also reports `pii_forward_queued`, `pii_forward_inflight`, `pii_forward_timeouts_total`, `pii_forward_hold_seconds_total` and `pii_forward_ms_per_token` alongside worker 0's model metrics (`pii_filter_input_tokens` histogram with buckets 128…64k — `_sum` is the token total, `pii_filter_windows_total`, `pii_filter_window_roundtrip_seconds`, `pii_filter_forward_duration_seconds`).
